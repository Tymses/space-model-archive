# SPACEMESHER

A minimal, source-linked archive for discovering space-related 3D models and preparing them for 3D printing.

## Project principles

- Preserve and document real-world scale wherever source data supports it.
- Keep original model files at their providers and retrieve them on demand through the Cloudflare Worker where supported.
- Show provenance and licence information alongside each model.
- Help users assess whether a model fits a selected printer's build volume.
- Support scale calculations and geometry-based fit checks where the source preview exposes measurable geometry.
- Do not integrate a slicer. Users prepare and slice files in their own software.

## Current interface

- Five collections: Spacecraft, Planetary features, Asteroids, comets & meteorites, Moons, and Terrain data & printable terrain. The first four are collections of physical objects and their model files; Terrain data & printable terrain is visually separated as a terrain collection for printable terrain meshes, elevation data and generators.

The Zenodo dataset comprises two NWA 869 meteorite-fragment sets and one terrestrial-rock-fragment set; it is not 868 distinct meteorite specimens. NASA Astromaterials 3D provides sample-specific high- and low-resolution OBJ ZIP downloads and states that its data is public domain with NASA credit requested.

Remote catalogue object pages are resolved through the Cloudflare Worker; only file URLs that pass a live byte-range probe are promoted to downloadable model records. Search and source/type filters apply across all four sections. Generators are not mixed into source catalogues or counted as downloadable model files.

It ranks source candidates, reports evidence quality and shows alternatives when evidence is ambiguous.
- Fit checks test all six axis-aligned 90° orientations.

## Remote model delivery

The Cloudflare Worker in `cloudflare/jpl-proxy.js` now supports a restricted `action=resolve` endpoint for individual 3D Asteroid Catalogue object pages. It extracts linked mesh files, validates the source host and extension, follows only allowlisted redirects and probes each candidate with a byte-range request. Selected files are then fetched through the existing `action=asset` endpoint; files are not mirrored into the GitHub repository. The asset allowlist includes Space Radar, NASA raw GitHub files, JPL radar OBJ files and 3D Asteroid Catalogue assets. The Worker must be redeployed manually in Cloudflare after changes to this repository; a GitHub Pages deployment alone does not update the Worker.

## Important limitations

- Missing real-world dimensions, scale, licence or geometry are never guessed.
- NASA models are linked to the NASA 3D Resources repository; follow NASA's usage guidelines and attribution requirements.
- The fit checker uses the 3D preview's bounding box. It is not a slicer simulation and does not check wall thickness, supports, bed adhesion, brim, collision clearance or arbitrary-angle packing.
- STL, OBJ, PLY, GLB and GLTF files can be previewed in the Scaling workspace. Draco/Meshopt-compressed glTF, GLTF companion files and OBJ/MTL assets are supported. A mesh-to-STEP conversion is not presented as a proper CAD solid unless its quality is verified.
- STEP support varies by slicer: Bambu Studio and PrusaSlicer support STEP import, while UltiMaker Cura's documented model formats do not list STEP. STL remains the broadly compatible fallback.
- The Scaling workspace can export the selected printable geometry as a binary STL in millimetres; the original source file remains unchanged.
- Scaling recommendations use the measured model geometry and verified physical dimensions. The original source file is not modified; the selected scale can be exported as a binary STL in millimetres.
- NASA Solar System Treks generates files based on the selected world and area, so the archive links to the portal rather than pretending there is one fixed model file.
- The curated asteroid, moon, comet and dwarf-planet entries now point to individual object pages as remote candidates. The source site does not document a public API, so the Worker discovers actual linked file URLs from each object page at request time. A candidate is not promoted until its mesh URL passes the Worker probe. Pages without a verified OBJ/PLY remain in Sources; direct endpoints and file sizes are never guessed.

## Catalogue completeness and data quality

- Collection records are classified by what they actually provide: direct mesh/CAD files, catalogue-page references, scientific dataset archives, viewers or generators. The collection interface no longer labels a source detail page as a direct model download; ZIP/7Z packages are separated from individual mesh files.
- The current audit snapshot is in [data/catalogue-audit.json](data/catalogue-audit.json). It reports 1,307 index records, 1,278 distinct source-file/listing placements after accounting for NASA's 29 cross-listed Height Map records, 977 direct mesh-file records (948 distinct source files after that cross-listing), 296 catalogue references, 29 archive packages and 5 unverified links. These are not unique physical-object counts.
- The audit and data rules are documented in [tools/catalogue/README.md](tools/catalogue/README.md). Rebuild the audit with `python tools/catalogue/audit_catalogue.py`.
- Source records are preserved individually. Multiple shape models, resolutions, methods and source datasets for the same physical object remain separate records; the audit never deletes or merges them. Only explicit numbered minor-planet designations are eligible for conservative cross-source grouping. Fuzzy name matches are not treated as proof of identity.
- The complete 3D Asteroid Catalogue inventory remains a priority: its reported 1,635 asteroids and 3,079 shape models are not fully imported. The current 256 asteroid object pages plus 37 moons, five comets and two dwarf planets are on-demand candidates, not a claim that all their meshes have already passed verification.

## Automated real-world dimension research

A first Python research pipeline for the 256 curated numbered asteroids is available in `tools/dimensions/`. It queries the official JPL Small-Body Database API, accepts only exact numbered-object matches, and writes tri-/bi-axial `extent` results to the separate candidate file `data/real-world-dimension-candidates.json`. Effective diameters are recorded separately and are never treated as longest axes.

GitHub Actions can run the scanner weekly or manually. Existing verified dimensions are skipped. The scanner does not modify `data/real-world-dimensions.json`; candidate values must be reviewed before they can affect scale calculations. See [the dimension research guide](tools/dimensions/README.md).

## Scaling & 3D Print workspace

The dedicated **Scaling & 3D Print** workspace is available from the top navigation and the bottom of the home page. Supported archive models expose a **Scaling** action in their detail view, which opens the workspace with the model file and any linked, verified real-world longest-axis measurement prefilled. The workspace also accepts local STL, OBJ, PLY and GLB uploads and displays an interactive 3D preview. Local uploads are processed in the browser and are not uploaded to SPACEMESHER.

The workspace supports millimetre, centimetre, metre and inch unit interpretation. External files also have an optional direct-diameter mode: enter the real object's original diameter and the desired printed diameter in millimetres to calculate the model scale without a verified longest-axis record. The collection breadcrumb uses “Asteroids & Comets” rather than the technical label “Small Bodies”. The GLB/glTF format uses metres by specification, while STL/OBJ/PLY units must be checked by the user. It calculates the source geometry dimensions, derives the original scale when a verified real-world reference is supplied, tests six axis-aligned 90° orientations against the selected printer volume, and suggests standard scale denominators. The built-in Bambu Lab P2S profile is 256 × 256 × 256 mm; custom build volumes can be entered. This is a bounding-box check, not a slicer simulation or a guarantee of printability. The source file is not modified. The selected printable scale can be exported directly as a binary STL in millimetres; the source file remains unchanged.

The workspace also provides three independent calculation modes. **Original astronomical scale** retains the source-backed physical-dimension workflow. **Fit to build plate** ignores astronomical scale, calculates the largest proportional geometry that fits the selected printer's usable volume, and applies a configurable safety margin (default 5 mm on every side) plus a proportional adjustment control. **Custom original dimensions** accepts a user-entered diameter, length, height or other measurement in mm, m or km; the user maps it to the matching model axis and the workspace derives the original denominator and printable standard scales while preserving all other proportions. The custom measurement is user-supplied, not source-verified. All modes compare resulting geometry with the selected build volume; the result remains a bounding-box check, not a slicer simulation. Fit mode checks six axis-aligned 90° orientations, but the exported STL retains the source orientation; rotate it in the slicer if the reported best orientation requires an axis swap.

The reference-length helper accepts km, m, cm or mm and includes a guide for finding a defensible longest-axis measurement. It directs asteroids/comets to the JPL Small-Body Database `extent` field, planets/moons to NASA mission science pages or PDS shape-model records, and other cases to the original scientific publication/dataset. The guide explains how to select the largest axis, handle radii versus full dimensions, and record the exact source URL. A single effective/mean diameter, unsourced summary or model-file bounding box is not silently treated as a verified longest axis.

## Automatic object scaling

The Scaling workspace derives a search term from an archive model name or uploaded filename. It checks the curated dimension index and JPL SBDB `extent` for small bodies first. If these do not return usable dimensions, the Cloudflare Worker searches the DuckDuckGo public web index, opens a limited set of promising pages, extracts candidate axes, ranks source quality and checks for conflicting values. High-evidence results may be selected automatically; when evidence is weak or conflicting, the best candidates are displayed for user review. This is a broad public-web search, not a crawl of every Internet page. The evidence score is heuristic, not a probability; measurement uncertainty is shown only when the source publishes it. A single effective diameter is never silently converted into three physical axes.

A one-time Cloudflare Worker setup is required because the JPL API does not enable browser CORS. Follow [the proxy setup guide](cloudflare/README.md) and set the Worker URL in `config.js`. The Worker source is [cloudflare/jpl-proxy.js](cloudflare/jpl-proxy.js).

## CORS-safe archive previews

GLB archive previews and all models opened in Scaling use a hybrid loading path: the browser fetches the original model URL first, then automatically retries through the configured Cloudflare Worker only if that direct request fails (for example, because the model host blocks CORS). Scaling measures the loaded mesh, and uses those same geometry bounds for its preview, original-scale calculation and printer-fit result. It supports GLB, glTF (including local or proxied `.bin`/texture companions), STL, OBJ (including `.mtl`/textures) and PLY.

The Worker is not deployed by a GitHub push. To enable the fallback, manually replace the code in the deployed Cloudflare Worker with the complete current [`cloudflare/jpl-proxy.js`](cloudflare/jpl-proxy.js), select **Deploy**, and keep its resulting URL in [`config.js`](config.js). See [the deployment guide](cloudflare/README.md) for the fixed host allowlist, redirect, private-network and 75 MB safeguards.

## Browser-based STL conversion

Supported non-STL source formats can be converted locally in the browser: FBX, 3DS, LWO, Blender `.blend`, STEP and STP. Compressed STEP files labelled `STEP (GZIP)` are normalized to the STEP parser after their GZIP payload is decompressed. Conversion uses Three.js STL export for the loaded geometry and OpenCascade for STEP tessellation. The Blender importer validates the `BLENDER` file signature, pointer size, byte order and embedded version before parsing. It supports little-endian Blender files; a different byte order is rejected explicitly. GZIP-compressed Blender files are streamed through a 75 MB decompressed-size limit. Zstandard-compressed files are size-checked after decompression; the decompressor may allocate its output before that check. The source download is checked against the 75 MB limit using both the declared response length (when supplied) and the received byte count. A valid file header does not guarantee that every Blender version or scene structure is supported; parser failures are reported separately.

The importer keeps valid mesh objects when another mesh object in the same scene is malformed, and reports the skipped objects. If no valid triangle mesh remains, the preview fails with object-level diagnostics. It does not invent missing polygon topology or replace the model with substitute geometry. The importer selects only Blender's canonical vertex-position and loop-vertex-index layers; legacy polygons are triangulated with exactly `n - 2` triangles per face. Unsupported or complex scenes should be opened in Blender and exported as GLB or STL for a more reliable conversion path. The browser workflow retains a 75 MB input/output limit and 5-million-triangle conversion limit. GZIP STEP decompression is streamed and stops if the uncompressed model exceeds 75 MB. Before STL export, SPACEMESHER estimates the binary STL size from the mesh triangle count and rejects outputs above 75 MB before allocating the export buffer; the final exported size is checked again. Very large or unsupported scenes may still fail and should be checked in a dedicated CAD/mesh tool.

The **Convert to STL** action is placed in the top-right title row of the model **View details** page (Position A). It is not shown on collection preview cards. See [the project handbook](PROJECT_HANDBOOK.md) for the required repository workflow, current implementation notes and verification status.


### STL conversion status

The browser-based **Convert to STL** action is marked **BETA** wherever it is offered. Conversion may not work for all models or file formats. It remains a best-effort browser conversion; inspect every exported STL in your slicer before printing.
